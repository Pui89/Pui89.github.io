PUI89 · WORK INTELLIGENCE · OPERATING MODEL

Increase work capacity.
Keep evidence in control.

A shared operating model for expanding PUI89 research and engineering throughput across projects—using event-driven automation, reusable workflows, explicit ownership and evidence-based review.

Implementation status: This page defines the proposed operating architecture. The role cards below are not autonomous agents currently running. No background agent, paid API, cloud GPU, new subscription or external credential is activated by this page.

One work pipeline across PUI89

Every work item should move through the same traceable stages. Automation can prepare and verify work; humans retain authority over consequential decisions.

01 · INTAKECapture a task

Record problem, project, source, expected outcome and constraints.

02 · TRIAGEPrioritise safely

Check value, dependencies, cost, risk and evidence required.

03 · EXECUTEWork in a branch

Use bounded scripts, local checks and reviewed GitHub workflows.

04 · VERIFYTest and inspect

Run checks, record failures and compare expected with actual results.

05 · APPROVEReview and publish

Human approval before merge, release, external messages or risky actions.

Automation opportunities without more scheduled tasks

Prefer event-driven automation over frequent polling. It can increase throughput without consuming one of the limited scheduled-task slots.

GITHUB EVENTS

Pull request and commit checks

  • Run tests when a pull request is opened or updated.
  • Validate documentation, links, JSON and project contracts.
  • Publish check results and artifacts only where useful.

Existing workflows must be inspected before adding or changing automation.

ISSUE EVENTS

Structured task intake

  • Use issue templates for bugs, research tasks and engineering proposals.
  • Apply labels for project, priority, risk and evidence status.
  • Link issues to branches, commits and pull requests.

Public issues must never contain secrets, personal data or sensitive operational details.

RELEASE EVENTS

Evidence and release records

  • Generate a commit-specific verification summary.
  • Record passed, failed, skipped and unknown checks separately.
  • Require human review before release or publication.

A green CI result proves only that the named checks passed for that commit.

REPOSITORY EVENTS

Maintenance and resilience

  • Review dependency updates and licence changes.
  • Check branch protection and least-privilege workflow permissions.
  • Preserve version history and test recovery procedures.

Do not enable new metered services or third-party actions without cost and trust review.

Autonomy and approval boundaries

AUTOMATABLE AFTER REVIEW

Low-risk repeatable work

Read public documentation, run tests, validate formatting, build reports from verified records, detect broken links and prepare draft pull requests.

HUMAN APPROVAL REQUIRED

Consequential actions

Merge or release, alter branch protection, delete or overwrite data, change credentials or permissions, contact external partners, spend money, or command physical hardware.

Strict zero-cost and evidence contract

Cost and security

  • No paid API, subscription, cloud GPU, model download or metered service by default.
  • No secrets in source code, public issues, logs or test fixtures.
  • Use least privilege, short-lived credentials where needed and revocation paths.
  • Check GitHub Actions minutes, artifact retention and external action licences before expansion.

Evidence and integrity

  • Attach repository, branch, commit SHA, date, command and result to verification records.
  • Separate measured, synthetic, estimated, proposed and unknown information.
  • Never convert missing evidence into a pass or invent progress percentages.
  • Keep changes on feature branches and use protected pull requests.
Current limitation: this operating model is documentation and website presentation only. It does not create a task backend, run agents, schedule monitoring, change repository settings or execute GitHub Actions.
